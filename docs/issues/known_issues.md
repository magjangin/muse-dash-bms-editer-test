## 🔧 A. 조건 블록을 제대로 다루기

> [!NOTE]
> ✅ **완료.** 지금은 `#RANDOM`/`#IF`/`#SWITCH` 가 든 차트도 **저장됩니다.**
> 노트가 어느 갈래에 속하는지를 `BranchId` 로 들고 있고,
> [`BmsWriter`](../../muse%20dash%20bms%20editer/Services/BmsWriter.cs) 가 `(마디, 갈래, 레인)` 으로 묶어
> **갈래별로 나눠 씁니다.** 조건 줄은 원본 줄 순서를 달고 제자리를 지킵니다.
> `SaveBms` 에는 저장을 막던 가드가 **더 이상 없습니다.**

### 🟡 남은 한계 — 갈래를 골라 볼 수는 없습니다

에디터는 조건 블록 **안의 노트를 전부 한 화면에** 그립니다. 갈래 1과 갈래 2가 같은 자리에 있으면
**겹쳐 보이고**, 지금 어느 갈래를 편집하는지 **고를 방법이 없습니다** — `BranchId` 를 읽는 화면이 하나도 없습니다.
새로 찍는 노트는 갈래 밖(`BranchId = 0`)으로 들어갑니다.

조건 차트는 **열고 저장하는 데까지는 안전**하지만 **갈래를 손보는 작업에는 아직 맞지 않습니다.**
🎹 [건반 BMS 다운믹스](../guides/keyboard_bms_downmix.md)가 조건 차트를 거절하는 것도 같은 이유입니다.

### 🗒️ 무엇이 위험했는가 (막아 두기 전의 손상 기록)

이 에디터는 조건 블록 안의 건반 줄을 평범한 노트로 읽습니다.
저장할 때 같은 마디·레인이면 한 줄로 합쳐지므로, 갈래별로 달랐던 패턴이
**항상 동시에 나오는 하나**가 됩니다. 조건 줄 자체도 데이터 줄이 아니라 헤더 블록으로 끌려 올라갑니다.

```
=== 원본 ===                    === 막기 전 저장 결과 ===
#00101:01                       #RANDOM 2
#RANDOM 2                       #IF 1
#IF 1                           #ENDIF          <-- 속이 빈 껍데기
#00111:01000000                 #IF 2
#ENDIF                          #ENDIF          <-- 속이 빈 껍데기
#IF 2                           #WAV01 a.wav
#00111:00001000                 #00101:01
#ENDIF                          #00111:0110     <-- 두 갈래가 하나로 합쳐짐
```

**어떻게 고쳤나**: 노트에 조건 맥락(`BranchId`)을 달고, 라이터가 갈래별로 나눠 씁니다.
보존줄에 원본 줄 순서를 달아 조건 줄이 제자리를 지키게 한 것도 같이 들어갔습니다 — 위 NOTE 참고.

## 🔊 B. 키음 믹싱 재생

> [!NOTE]
> ✅ **완료.** [KeySoundPlayer.cs](../../muse%20dash%20bms%20editer/Services/KeySoundPlayer.cs) 는
> **자기 `waveOut` 스트림에 여러 음을 합산**해 내보냅니다(폴리포닉).
> WAV(8/16/24/32bit PCM · IEEE Float · Extensible)와 OGG 를 **PCM 으로 미리 풀어** 두고,
> 믹서 스레드가 살아 있는 보이스(`_activeVoices`)를 더하면서 클리핑을 막습니다.
> **화음도 긴 키음도 안 끊깁니다.**
> `PlaySound` 는 **디코딩이 실패했을 때의 비상구**로만 남아 있습니다(`PlaySoundFallback`).

아래는 **그 전 상태의 기록**입니다. 왜 이 항목이 있었는지 남겨 둡니다.

* 예전에는 Win32 `PlaySound(SND_ASYNC)` 하나라 **새 소리가 앞 소리를 끊었습니다**
* 같은 자리의 화음은 **마지막 한 음만** 들렸고, 긴 키음은 다음 노트에서 잘렸습니다
* 노트마다 파일 경로로 디스크에서 다시 읽었습니다 (미리 풀어둔 PCM이 없었습니다)

재생 중에 들리는 건 곡이 아니라 "마지막 노트들"이었고, 채보를 귀로 검수할 수 없었습니다.

### 어떻게 만들었나 — 명령별 역연산이 아니라 통째 스냅샷

처음 적어 둔 방향은 "편집 메서드마다 명령 기록을 끼운다"였습니다. **그 방향을 쓰지 않았습니다.**
편집 기능이 늘 때마다 역연산을 같이 적어야 하는데, 그게 이 저장소가 반복해서 데인 실패 모양
(같은 일을 두 곳에 적었다가 한쪽만 고침)이기 때문입니다.

대신 **모든 편집 경로가 지나가는 한 곳**([`NotifyNotesChanged`](../../muse%20dash%20bms%20editer/ViewModels/MainWindowViewModel.Editing.cs))
에서 문서를 통째로 떠 둡니다. 빠뜨릴 경로가 없습니다.

| 담는 것 | 왜 |
|:---|:---|
| 노트 전부 (**복제본**) | 이동·키음 교체는 `BmsNote` 를 제자리에서 고친다. 참조만 담으면 되돌릴 것까지 같이 바뀐다 |
| 키음 목록 · `#WAV` 표 | 노트만 되돌리면 지운 번호를 가리키는 유령 노트가 생긴다 |
| 선택 (자리 번호로) | 되돌렸을 때 어디가 되돌아갔는지 보이게. 선택 자체는 칸을 쌓지 않고 지금 칸만 따라간다 |

담지 않는 것: **헤더(제목·BPM·난이도)와 화면 설정(줌·보기 방향)**. 노트를 되돌렸는데 BPM 까지
옛날 값으로 돌아가면 그게 더 놀랍습니다.

* 상한 **100칸**([`EditHistory.MaxDepth`](../../muse%20dash%20bms%20editer/Services/EditHistory.cs)). 넘으면 오래된 것부터 버립니다
* 문서를 새로 열거나 비우면 기록을 지웁니다. 이전 문서의 노트가 튀어나오면 안 됩니다
* 비용 실측: **노트 1000개 차트에서 편집 100회 + 되돌리기 100회에 483ms** (한 번에 약 2.4ms,
  홀드 짝 다시 읽기까지 포함한 값입니다)

## 📉 D. 뷰포트 컬링

`NoteGridControl` · `OggWaveformControl` 이 매 프레임 타임라인 **전체**를 그립니다.
5분·BPM 150·16분할이면 격자선만 약 3,000개 × 2컨트롤, 192분할이면 약 36,000개 × 2.
재생 타이머가 33ms마다 위치를 바꾸므로 초당 30번 반복됩니다.

**남은 성능 항목 중 유일하게 값이 큽니다.** 곁가지 넷은 아래와 같습니다 (2026-09-21 코드 확인).

| 항목 | 상태 |
|------|------|
| 마디 라벨 `FormattedText` | ✅ **캐시됨.** `OggWaveformControl._measureLabelCache`(마디별) · `NoteGridControl._laneHeaderFormattedTextCache`(레인 머리글) |
| `Notes` 프로퍼티가 매번 배열 복사 | ✅ **없앰.** `NotifyNotesChanged()` 에서 `_notesCache` 를 한 번만 만들고, `SelectedNotes` 도 `_selectedNotesCache` 로 같게 |

| 편집마다 전체 재집계 | ❌ **그대로, 오히려 늘었음.** 통계·컨트롤 패널에 더해 이제 **홀드 짝 재계산(`RecomputeHolds`)** 도 편집 한 번마다 돕니다. 노트 1000개 차트에서 편집 1회 약 2.4ms 로 실측했습니다([C](#-c-undo--redo)) |

## 🟡 25-2. 비디오가 ScrollViewer 밖으로 삐져나온다

[VideoPreviewControl.cs](../../muse%20dash%20bms%20editer/Views/Controls/VideoPreviewControl.cs) 는
네이티브 창(HWND)이라 Avalonia 의 `ClipToBounds` 가 먹지 않습니다.
`_controller.Bounds` 를 좌표만 보고 잡는데, 오른쪽 패널을 스크롤하면 원점이 패널 밖으로 나갑니다.
툴바 위로 비디오가 삐져나올 수 있습니다.

**확인 방법**: 비디오를 띄운 채 오른쪽 패널을 위아래로 스크롤합니다.

**고칠 방향**: 부모의 보이는 영역과 교차한 사각형으로 `Bounds` 를 잘라 넣고,
완전히 벗어나면 `IsVisible = false` 로 둡니다.

## 🎛️ 되살린 것: 집계에서 키음으로 노트 찾기

한때 통계 창에 있었다가 **걷어냈던** 기능입니다. 이번에 **🎛️ 컨트롤 패널**이라는 별도 창으로 다시 만들어 넣었습니다.
(`ControlPanelViewModel` · `ControlPanelWindow`)

### 왜 접었었나

만드는 동안 세 번 헛돌았고, 매번 원인이 달랐습니다.

| 시도 | 무엇이 문제였나 |
|------|----------------|
| 1 | 명령을 `{Binding $parent[ItemsControl].((vm:NoteStatsViewModel)DataContext).…}` 로 끌어왔는데, 컴파일된 바인딩에서 **조용히 실패**했습니다. `Command` 가 null 인 버튼이라 눌러도 아무 일이 없었고, 빌드도 예외도 멀쩡했습니다 |
| 2 | 버튼 스타일(`Background`·`BorderBrush`)이 **Fluent 테마의 Button 템플릿에 가려** 화면에 안 나타났습니다. 누를 수 있다는 표시가 없으니 누를 생각을 할 이유도 없었습니다 |
| 3 | `ListBox` 로 바꿔 동작은 했지만, 고른 노트가 화면 밖이면 여전히 눌렸는지 알기 어려웠습니다. 격자를 그리로 스크롤하고 안내문을 붙이며 덧대다 보니 통계 창의 몫이 아닌 일이 늘었습니다 |

### 이번에는 무엇을 다르게 했나

| 예전에 걸린 것 | 이번 방식 |
|----------------|-----------|
| 목록 항목 안에서 조상 바인딩으로 명령을 끌어옴 | **목록 항목에는 명령을 걸지 않습니다.** 고른 줄은 `SelectedItem` 으로만 받고(`SelectedLaneStat`·`SelectedWavStat`), 누르는 것은 전부 목록 **밖**의 버튼입니다. 창의 `DataContext` 가 곧 뷰모델이라 바인딩이 한 칸도 건너뛰지 않습니다 |
| 버튼이 테마 템플릿에 가려 안 보임 | 항목 안에 버튼을 두지 않으니 가려질 자리 자체가 없습니다. 고른 줄은 검색 창·팔레트와 같은 파랑(`#3B6FD4`)으로 강조합니다 |
| 고른 노트가 화면 밖이면 눌렸는지 알 수 없음 | 선택을 `NoteSelectionSource.Search` 로 알려 **그 자리로 스크롤**시키고(`ScrollToRatioRequested`), 결과를 창 아래 한 줄(`StatusMessage`)로 말해 줍니다 |
| 뷰모델은 멀쩡한데 화면에서 끊어짐 | 창을 실제로 띄워 **작업 버튼 6개에 `Command` 가 붙어 있는지** 확인하는 테스트를 넣었습니다(`WindowSmokeTests`) |

검색 창과 역할이 겹치지 않느냐는 판단은 이렇게 갈랐습니다.
**"이 번호가 몇 개 있나"에서 곧장 손대는 것**은 컨트롤 패널이 맡고,
**"조건을 조합해 찾는 것"**(마디 범위 · 노트 종류 · 여러 레인)은 그대로 검색 창의 몫입니다.
컨트롤 패널의 일괄 작업은 언제나 **고른 줄 하나**를 대상으로 합니다.

> 📊 통계 창은 **보기 전용으로 남겨 두었습니다.** 숫자만 볼 때 잘못 눌러 수백 개가 바뀌는 일이 없고,
> 집계 규칙은 `NoteStatsViewModel` 한 곳뿐이라 두 창의 숫자가 갈라지지 않습니다.

> 되돌리기가 들어간 뒤에도([C](#-c-undo--redo)) 컨트롤 패널의 **일괄 삭제는 먼저 물어봅니다.**
> 확인 창을 띄울 길이 없으면(`ConfirmAsync` 가 없으면) 아무것도 지우지 않습니다.

### 🅿️ 나중에 고려: 패널 맨 위의 열(레인) 선택 칸

"레인별 노트 개수 + [레인 노트 선택]" 칸은 **모양을 다시 볼 자리로 남겨 둡니다.**
지금은 한 번에 레인 하나만 고를 수 있어서, 여러 열을 묶어 고르는 일은 검색 창의 열 토글이 더 낫습니다.
게다가 편집 대상 레인이 `16,11,12,13,14,15,18` 로 고정돼 있어 열 개수 자체가 바뀔 여지가 있습니다.
**어떤 모양이어야 하는지는 그때 정합니다.** 그 전까지는 지금 형태로 둡니다.

같이 볼 것: 다중 선택(여러 레인 한꺼번에), 1P/2P 묶음 표시, 검색 창의 열 조건과 역할 나누기.

## 🚫 확인해 보니 문제가 아니었던 것

점검 중 의심했으나 실제로 돌려 보니 정상이었던 것입니다. 같은 의심을 다시 하지 않도록 남깁니다.

| 의심한 것 | 결과 |
|-----------|------|
| `#PLAYER` 왕복이 한 칸씩 밀리지 않는가 (파일은 1/2/3, 콤보박스는 0부터) | **정상.** `PullHeaderFromChart` 의 `Player - 1` 과 `BmsWriter` 의 `player + 1` 이 짝을 이룹니다. 1→0→1, 2→1→2, 3→2→3 으로 세 값 모두 제자리로 돌아옵니다 |
| 데이터 줄 길이가 청크 크기로 안 나누어떨어지면 뒤가 잘리는가 | **잘리는 것은 맞지만** 규격을 벗어난 입력에서만 나옵니다(예: 9자 데이터 → 4개만 읽고 마지막 1자 버림). 우선순위가 낮습니다 |
| 빌드 경고 `MSB3277` (WindowsBase 4.0 vs 5.0) | **문제가 아닙니다.** WebView2가 끌고 오는 경고로 프로젝트당 1개씩 총 2개 납니다. `CoreWebView2` 만 쓰므로 동작에는 영향이 없습니다 |

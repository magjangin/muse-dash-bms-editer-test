짝 맞추기에 주는 함의는 하나입니다 — 같은 자리에 노트가 둘이면 **짝 순서가 정의되지 않으므로,
맞추려 하지 말고 🔴 로 지목하고 손을 뗍니다**(→ [§4 P3](#p3--검사기)).

> 레인별로 묶는 것은 홀드 구현의 **세부사항**이지 인터페이스가 아닙니다. 이 자리는 지금 정해야
> 나중에 엔진을 두 번 안 고칩니다.

두 기계를 따로 구현합니다.

| | 홀드·샌드백 | in/out |
|:---|:---|:---|
| 묶는 단위 | 채널별 | **차트 전체** |
| 순서 | 시작 → 끝 | **out → in** |
| 대기 | 토글 (1을 안 넘음) | **덮어쓰기** — 밀려난 out을 기록해 뒀다 진단으로 올림 |
| 종류 분리 | Hold / Sandbag 따로 | 하나 |

재계산은 [`NotifyNotesChanged()`](../../muse%20dash%20bms%20editer/ViewModels/MainWindowViewModel.Editing.cs) **한 곳**에서만 합니다.
편집 경로 9개가 전부 여기를 지나는 것을 확인했습니다. 정렬은 옆의 `GetSortedNotes()` 를 그대로 씁니다.

**완료 판정**: 실측 차트(340노트)를 열면 홀드·샌드백·in/out 짝 수가 나온다 · **열었다 바로 저장하면 바이트가 동일하다**.

### P2 · 표시 ← **여기가 이 계획의 본론**

| | |
|:---|:---|
| 크기 | **중간** |
| 바꾸는 것 | [`NoteGridControl.Render`](../../muse%20dash%20bms%20editer/Views/Controls/NoteGridControl.cs) |
| 파일 변경 | ❌ 없음 |

* **홀드·샌드백**: 레인 안에서 시작~끝을 **몸통**으로 잇습니다.
* **in/out**: 레인을 **가로지르는 연결선**입니다. 몸통 코드를 재사용할 수 없습니다(F-7).
* 종류별로 모양·색을 다르게(장애물·고스트·하트).
  동그라미 노트 안에 **종류별 이미지**를 넣는 방법과 이미지 크기(1:1, 64×64 권장)는
  [🟢 note_circle_icon.md](note_circle_icon.md) 에 따로 적었습니다.
* 고아는 몸통 없이 **점선 캡 + 경고색**.
* 시작·끝 좌표를 **각각** `ChartTimeline.SecondsAt()` 으로 구합니다.
  마디 단위 선형 보간을 쓰면 BPM 변화·변박을 지나는 몸통 끝이 어긋납니다.
* 격자는 **세로·가로 보기 둘 다** 있습니다. 양쪽에 그려야 합니다.

> [!NOTE]
> **검사기(P3)보다 이쪽이 먼저인 이유.**
> 출현 순서 방식에서는 *"처음 어긋난 자리"* 를 **파일만 보고는 알 수 없습니다.** 홀드류가 짝수 개면
> `(1,2)(3,4)(5,6)…` 은 구조적으로 전부 정상이고, 사용자가 다른 짝을 의도했다는 사실이 파일 어디에도
> 안 적혀 있습니다. 깨진 데가 없는데 "깨진 곳"을 지목할 수는 없습니다.
>
> 대신 **몸통을 그으면 47~49마디가 홀드고 50~52마디가 빈칸이라는 게 눈으로 즉시 보입니다.**
> 4시간이 날아간 이유는 탐지 불가능한 오류가 아니라 **아무것도 안 보였기 때문**입니다.

**완료 판정**: 340노트 차트에서 홀드가 막대로 보인다 · BPM 변화 구간을 지나는 몸통 끝이 끝 노트와 만난다 · **같은 규모를 다시 만들어 시간을 재고 [authoring_time.md](../issues/authoring_time.md) 에 두 번째 줄을 적었다**(U-1).

### P3 · 검사기

| | |
|:---|:---|
| 크기 | **중간** |
| 바꾸는 것 | 진단 목록 패널 · 상태 표시 |
| 파일 변경 | ❌ 없음 |

| 진단 | 게임에서 어떻게 되는가 | 수준 |
|:---|:---|:---:|
| `OrphanHead` | 짝 없는 홀드/샌드백 시작 → **단타로 강등** | 🔴 |
| `OverwrittenOut` | out 대기 중 또 out → **앞의 out이 조용히 소멸** | 🔴 |
| `UnresolvedBossTarget` | 짝은 맞았는데 **이벤트가 안 생김** (F-11) | 🔴 |
| `OrphanOut` / `OrphanIn` | 짝 없는 보스 전환 → 아무 일도 안 일어남 | 🔴 |
| `ReversedInOut` | in을 out보다 먼저 찍음 → **통째로 무효** | 🔴 |
| `DuplicateAtSamePosition` | 짝 순서 미정의 + **저장하면 하나가 사라짐** (2-2) | 🔴 |
| 말이 안 되는 몸통 길이 | 수열이 밀렸다는 **눈에 보이는 증상** | 🟡 |
| 길이 0 홀드 | U-2 미확인 | 🟡 |

> [!IMPORTANT]
> **in/out 진단이 홀드보다 값이 큽니다.**
> 홀드는 실패하면 게임이 `[BmsMatcher.Bug]` 를 찍어 줍니다. **in/out은 로그가 한 줄도 없습니다.**
> 특히 `UnresolvedBossTarget` 은 게임 로그에 `보스 스왑 후보` 줄이 **그냥 안 보일 뿐**이라
> 무엇이 없는지 알아채는 데만 한참 걸립니다.

진단 문구는 **"에디터가 뭘 못 했는지"가 아니라 "게임에서 어떻게 될지"** 로 씁니다. 위 표의 가운데 칸이 곧 문구입니다.
목록에서 고르면 그 자리로 격자가 스크롤됩니다 — `SetNoteSelection(..., NoteSelectionSource.Search)` 경로가 이미 있습니다.
🔴 가 있어도 **저장은 막지 않습니다.** 작업 중간에는 당연히 짝이 안 맞습니다.

**완료 판정**: 340노트 차트에서 🔴 0건이 나오고, 게임 로그의 짝 경고도 0줄이다(게임 실행 1회).

### 이 계획이 틀릴 수 있는 지점

* **U-1이 전제입니다.** 몸통을 그리면 빨라진다는 것은 **가설**입니다. 4시간의 절반이 검증 왕복이었다는
  기록에서 나온 추정이지, 측정된 값이 아닙니다. P2 후 재봐서 안 줄면 P3 이후를 다시 짜야 합니다.
* **340노트 한 번이 실측 전부입니다.** 다른 곡·다른 난이도에서 시간 배분이 같으리란 보장이 없습니다.
* in/out은 **개수가 적어 실제 체감이 작을 수 있습니다.** 값이 큰 이유는 빈도가 아니라
  **실패가 조용해서** 입니다. 빈도로 우선순위를 다시 매기면 뒤로 갈 수 있습니다.

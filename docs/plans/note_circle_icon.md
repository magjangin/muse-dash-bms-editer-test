# 🟢 노트 동그라미 안에 이미지 넣기 — 되는지와 크기

> [!NOTE]
> * 작성일: **2026-09-13**
> * 상태: **확인 완료 · 아직 구현 안 함.** 코드는 한 줄도 고치지 않았습니다.
> * 상위 계획: [🗺️ muse_dash_specialization.md](muse_dash_specialization.md) 의 **P2 · 표시**

뮤즈 대시는 노트(몬스터) 종류가 많아서, 격자의 **동그라미 노트 안에 종류별 이미지**를 넣으려 합니다.
이 문서는 ① 지금 로직으로 되는지, ② 이미지 파일을 **몇 대 몇, 몇 픽셀**로 만들어야 하는지를 적습니다.

---

## 0. 결론

| 질문 | 답 |
|:---|:---|
| 되는가? | **됩니다.** 실제로 그려서 픽셀까지 확인했습니다(§4) |
| 선명하고 눈에 잘 들어오나? | **15px(지금)에서는 아니요** — 색 덩어리로만 보이고 어두운 그림은 검은 격자에 묻힙니다. **굵은 윤곽·밝은 색 그림을 30px로 키워야** 알아볼 만합니다 (2026-09-13, 대체 그림 3종을 격자 배경에 그려 눈으로 확인) |
| 비율 | **1:1 (정사각형)** |
| 원본 크기 | **64×64 px 권장** · 최소 32×32 px |
| 형식 | **PNG, 투명 배경** |
| 그리는 방식 | **노트마다 자르지 말고, 크기별로 한 번 미리 동그랗게 구워 둔다** — 노트마다 자르면 느립니다(§4) |
| 클릭·선택 코드 | **안 고쳐도 됩니다.** 이미지 크기와 무관합니다(§1-3) |

## 1. 지금 로직 (코드에서 확인)

### 1-1. 동그라미 크기

[`NoteGridControl.Render`](../../muse%20dash%20bms%20editer/Views/Controls/NoteGridControl.cs) 가 세로·가로 보기 **두 곳**에서 같은 식을 씁니다.

```csharp
var radius = Math.Min(7.5, (laneThickness - 4) / 2);   // laneThickness = LaneWidth(40) × HorizontalZoom
context.DrawEllipse(noteBrush, NoteOutlinePen, center, radius, radius);   // 테두리: 검정 1px
```

즉 **지름 = `min(15, 40 × 가로줌 − 4)` px** 입니다.

| 가로 줌 | 레인 폭 | 동그라미 지름 |
|:---:|:---:|:---:|
| 0.25 (최소) | 10 px | 6 px |
| 0.40 | 16 px | 12 px |
| **0.475 이상** | 19 px 이상 | **15 px (상한)** |
| 1.50 (기본) | 60 px | **15 px** |
| 4.00 (최대) | 160 px | 15 px |

> **기본 상태에서 동그라미는 15px로 고정입니다.** 레인이 넓어져도 커지지 않습니다(`7.5` 상한이 코드에 박혀 있음).
> 테두리 1px가 가장자리를 덮으므로 **이미지가 실제로 보이는 폭은 약 14px** 입니다.

동그라미 모드는 사용자가 켜는 옵션입니다 — 체크박스 *"네모를 동그라미로 바꾸기"*(`IsCircleNoteShape`, 기본 꺼짐).
네모 모드는 기본 **56×6 px** 라 이미지를 넣을 자리가 없습니다. **이미지는 동그라미 모드에서만** 넣습니다.

### 1-2. 같은 레인 이웃 노트와의 간격 — 동그라미가 이보다 크면 겹칩니다

격자 한 칸의 시간은 `240 / (BPM × 분할)` 초이고, 화면의 초당 픽셀은
`RowHeight × 세로줌 × (분할 / GridMeasure) / 2` 입니다([`TimelineControlBase.GetTimelineHeight`](../../muse%20dash%20bms%20editer/Views/Controls/TimelineControlBase.cs)).
둘을 곱하면 **분할 수가 지워집니다.** 기본값(`RowHeight 16`, `GridMeasure 4`)을 넣으면:

```
음원이 있을 때:  칸 간격(px) = 480 × 세로줌 / BPM
음원이 없을 때:  칸 간격(px) = 4 × 세로줌            (BPM 무관)
```

세로 줌 슬라이더 범위는 **4 ~ 8**, 기본 **8** 입니다. 음원이 있을 때 표입니다(동그라미끼리 1px씩 띄우려면 **지름 ≤ 간격 − 2**).

| BPM | 세로줌 8 (기본): 간격 → 넣을 수 있는 최대 지름 | 세로줌 4 (최소): 간격 → 최대 지름 |
|:---:|:---:|:---:|
| 100 | 38.4 → **36** | 19.2 → **17** |
| 120 | 32.0 → **30** | 16.0 → **14** |
| 150 | 25.6 → **23** | 12.8 → **10** |
| 180 | 21.3 → **19** | 10.7 → **8** |
| 200 | 19.2 → **17** | 9.6 → **7** |
| 240 | 16.0 → **14** | 8.0 → **6** |

> [!WARNING]
> **지금 15px 동그라미도 이미 겹치는 구간이 있습니다.**
> 세로줌 8에서는 **BPM 226 초과**, 세로줌 4에서는 **BPM 113 초과**부터 **같은 레인 16분 연타**의 동그라미가 겹칩니다.
> 단색일 때는 티가 덜 나지만, **이미지를 넣으면 뭉개져 보입니다.**
> (표는 "지금 분할 수의 격자 칸" 기준입니다. 더 촘촘한 위치에 찍힌 노트는 그만큼 더 가깝습니다.)

### 1-3. 클릭·선택은 이미지 크기와 무관합니다

| 동작 | 무엇을 보나 | 이미지 크기 영향 |
|:---|:---|:---:|
| 좌클릭 배치 | 클릭한 **격자 위치** → 마디·위치로 스냅 | ❌ 없음 |
| 우클릭 삭제 | 격자 위치 기준 가장 가까운 노트 | ❌ 없음 |
| 드래그 선택 | 노트 **중심점**이 사각형 안에 있는지 | ❌ 없음 |
| 선택 강조 테두리 | 노트 중심 ±7px 사각형 | ⚠️ **동그라미를 키우면 같이 키워야 함** |

선택 강조 사각형 높이가 14px라서, 지금 15px 동그라미도 0.5px씩 삐져나와 있습니다. 크기를 바꿀 때 `지름 + 4` 로 맞춥니다.

## 2. 🖼️ 이미지 파일 사양 — 그림 만드는 쪽이 볼 표

| 항목 | 값 | 이유 |
|:---|:---|:---|
| **비율** | **1:1** | 동그라미 칸이 정사각형입니다 |
| **권장 크기** | **64×64 px** | 앞으로 키울 최대 표시 크기 30px(§3) × 윈도우 배율 200% = 60 실제 픽셀을 **확대 없이** 덮습니다 |
| **최소 크기** | 32×32 px | 지금 15px × 200% = 30 실제 픽셀 |
| 더 큰 원본 | 128×128 까지는 괜찮음 | 불러올 때 표시 크기로 바로 줄여 읽으므로(§3-2) 메모리 문제는 없지만, 얻는 것도 없습니다 |
| **형식** | **PNG, 투명 배경** | 동그라미 바깥이 투명해야 격자선이 보입니다 |
| **여백** | 중요한 부분은 **가운데 지름 약 85~90% 원 안에** (64px 기준 가운데 약 56px 원) | 네 모서리는 잘리고, 가장자리 1px는 검은 테두리가 덮습니다 |
| 그림 방향 | 세로·가로 보기 모두 **회전 없이** 그대로 | 코드가 이미지를 돌리지 않습니다 |

> [!IMPORTANT]
> **실제 보이는 크기는 약 14px입니다.** 64px에서 그린 디테일은 거의 다 사라집니다.
> 얼굴 표정·작은 무늬보다 **실루엣과 주 색상**이 구분되게 만드는 편이 결과가 낫습니다.
> 종류가 비슷한 몬스터끼리는 15px에서 **구별이 안 될 수 있습니다**(→ §5 미확인 항목).

### 크기가 왜 논리 픽셀과 실제 픽셀로 나뉘나

코드의 15px는 **논리 픽셀**입니다. 윈도우 디스플레이 배율이 걸리면 실제 픽셀은 그만큼 늘어납니다.

| 윈도우 배율 | 지금 15px 동그라미의 실제 픽셀 | 30px로 키웠을 때 |
|:---:|:---:|:---:|
| 100% | 15 | 30 |
| 125% | 19 | 38 |
| 150% | 23 | 45 |
| 200% | 30 | **60** |

권장 64×64는 이 표의 **가장 큰 값(60)** 을 확대 없이 덮는 크기입니다.

## 3. 🛠️ 구현 방법 (제안)

### 3-1. 크기 — 두 단계로 나눕니다

| 단계 | 지름 | 바뀌는 것 | 위험 |
|:---:|:---|:---|:---:|
| **1단계** | **15px 그대로** | 단색 채움 → 이미지로만 교체 | 낮음 |
| 2단계 (선택) | `min(레인폭 − 4, 칸간격 − 2, 30)` | 동그라미 크기 식 · 선택 강조 테두리 | 중간 |

* 1단계는 레이아웃·입력을 전혀 안 바꿉니다. **이미지가 15px에서 알아볼 만한지 먼저 봅니다.**
* 2단계의 `칸간격` 은 **차트에서 가장 빠른 BPM** 기준이어야 BPM이 빨라지는 구간에서 안 겹칩니다.
  [`ChartTimeline`](../../muse%20dash%20bms%20editer/Services/ChartTimeline.cs) 에는 지금 `BaseBpm` · `HasBpmChanges` 만 있고 **최대 BPM을 묻는 방법이 없어 추가가 필요합니다.**
* 상한 30은 기본 레인 폭(60px)과 BPM 120·세로줌 8의 간격(32px)에서 나온 값입니다. 바꿀 수 있습니다.

### 3-2. 그리는 방식 — **노트마다 자르지 않는다**

```
불러올 때:  PNG → Bitmap.DecodeToWidth(표시크기×배율)  → 동그라미로 한 번 잘라 굽기 → 캐시
그릴 때:    context.DrawImage(구운 이미지, 노트 사각형)   → 그 위에 검은 테두리 1px
```

* 캐시 열쇠는 **(이미지, 실제 픽셀 크기)** 입니다. 줌이나 윈도우 배율이 바뀌어 크기가 달라질 때만 다시 굽습니다.
* 실제 픽셀 크기 = `round(지름 × 창의 RenderScaling)`.
* 이미지가 없는 종류는 **지금처럼 단색 동그라미**로 둡니다.

노트마다 `PushGeometryClip` 으로 자르면 느린 이유는 §4 의 측정값입니다. 이 격자는 재생 중 **33ms마다 전체 노트를 다시 그리고**,
화면 밖 노트를 건너뛰는 처리도 없습니다([known_issues.md](../issues/known_issues.md) D 항목 — 렌더 무결성 때문에 걷어냄).

### 3-3. 어느 이미지를 쓰나 (제안 · 미확정)

```
note_icons/<UID 6자리>.png   → 있으면 이것
note_icons/<종류>.png        → 없으면 종류별 (홀드 · 샌드백 · 하트 · 장애물 · 고스트 · 보스 …)
(없음)                        → 지금처럼 단색 동그라미
```

* 종류 판별은 계획 문서 P0의 UID 분류기(**prefix 우선**)를 그대로 씁니다.
* 폴더는 **exe 옆 외부 폴더**로 둡니다. 게임에서 뽑은 그림이라 exe 안에 넣어 배포하지 않는 편이 맞습니다.
* **어느 UID가 게임에서 어떤 몬스터 그림으로 나오는지는 아직 모릅니다**(§5 U-C).

## 4. ✅ 확인 기록 (2026-09-13)

테스트 프로젝트의 헤드리스 렌더러(Avalonia 12.0.5 + Skia)에서 **실제로 그리고 픽셀을 읽어** 확인했습니다.
확인용 테스트는 끝난 뒤 지웠습니다.

### 되는지

| 확인 | 결과 (B, G, R, A) | 판정 |
|:---|:---|:---:|
| 64×64 빨간 네모를 동그라미로 잘라 그림 — 모서리 (1,1) | (0, 0, 0, **0**) 투명 | ✅ |
| 같은 그림 — 가운데 (32,32) | (0, 0, 255, **255**) 빨강 | ✅ |
| 지름 15px로 줄여 그림 — 모서리 / 가운데 | 투명 / 빨강 | ✅ |
| PNG로 저장했다 다시 읽기 | 64×64 그대로 | ✅ |
| `CreateScaledBitmap` · `DecodeToWidth` 로 30px 줄이기 | 둘 다 30×30 | ✅ |
| 30px로 미리 동그랗게 굽기 — 모서리 / 가운데 | 투명 / 빨강 | ✅ |

> 중간에 한 번 실패했습니다 — `CreateScaledBitmap` 에 **렌더 결과 비트맵**을 넘기면 `Invalid source bitmap type` 예외가 납니다.
> **PNG에서 읽은 비트맵**은 정상입니다. 실제 아이콘은 PNG에서 읽으니 문제는 아니지만, 구울 때 이 순서를 지켜야 합니다.

### 속도 — 노트 5000개를 한 프레임에 그릴 때

| 방식 | 프레임당 | 재생 타이머 33ms 대비 |
|:---|:---:|:---|
| 노트마다 동그라미로 잘라서 64px 원본 그리기 | **66.9 ms** | ❌ 두 배 넘게 초과 |
| **미리 구운 30px 이미지를 자르지 않고 그리기** | **20.9 ms** | ✅ |
| (참고) 지금의 단색 `DrawEllipse` | 34.9 ms | — |

> [!NOTE]
> **절대값은 참고용입니다.** 헤드리스 CPU 렌더링이라 실제 창(GPU)과 숫자가 다릅니다. 의미 있는 것은 **순서**입니다 —
> 노트마다 자르는 방식이 가장 느리고, 미리 구운 이미지는 지금 도형보다도 빠릅니다.
> 실측 차트 규모(340노트)로 줄이면 대략 4.5ms / 1.4ms / 2.4ms 수준이라 어느 방식이든 느끼기 어렵습니다.
> **노트가 수천 개인 곡에서 차이가 납니다.**

## 5. ⬜ 확인 안 된 것

| # | 모르는 것 | 확인 방법 |
|:--:|:---|:---|
| U-A | **15px에서 몬스터 그림을 알아볼 수 있는가** | 1단계 구현 후 실제 아이콘 몇 개로 화면을 캡처해 봄. 안 되면 2단계로 |
| U-B | 실제 차트의 BPM 범위 · 같은 레인 최소 간격 | 이번에 확인 못 함 — 뮤즈 대시가 두 Steam 라이브러리(`C:\Program Files (x86)\Steam`, `H:\SteamLibrary`) 어디에도 설치돼 있지 않아 `hwa` 폴더의 차트를 못 읽었습니다. 위 표는 BPM 범위로 대신했습니다 |
| U-C | 어느 UID가 게임에서 어떤 몬스터 그림인가 | 게임 데이터 확인이 필요합니다. 그 전까지는 **종류별 아이콘**만 확실합니다 |
| U-D | 실제 창(GPU)에서의 속도 | 수천 노트 곡을 열고 재생해 봄 |
